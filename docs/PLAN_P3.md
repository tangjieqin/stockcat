# PLAN_P3 资料检索（P3）实施计划

- 编写时间：2026-10-27
- 状态：**P3.0–P3.4 全部完成（2026-10-27），P3.5 判定不做**
- 上游依据：`PRD.md` §P3、`DEVELOPMENT_PLAN.md` P3、`BACKLOG.md` §2.3
- 关系：P2 的 AI 能力已有四个场景（问答 / 告警解释 / 复盘草稿 / 日记辅助），P3 给它们补"外部资料"这一层来源

## 0. 结论摘要

P3 的目标不是"做一个能聊资料的机器人"，而是**让资料可查、引用可信**。三条线：

1. **导入**：手工粘贴 + 本地文件（`.md` / `.txt` / `.html`），不做爬虫。
2. **检索**：关键词检索（`ILIKE` + 中文 bigram 切词 + 片段排序），**不引入 pgvector**，切片保留原文偏移，引用能回到原段落。
3. **接入**：新增只读工具 `library-search`，让 P2 的四个场景在需要时引用资料；引用必须来自检索返回的片段 ID，不接受模型自述出处。

拆四批：P3.1 导入与切片 → P3.2 检索页 → P3.3 工具接入 → P3.4 评估。向量检索列为 P3.5，**是否做由 P3.4 的评估结果决定**。

**P3.0 已完成（2026-10-27）**：`bigram + ILIKE` 的 `recall@5 = 0.974`，通过 0.70 门槛，
关键词路线继续；`pg_trgm` 被排除（中文短查询失效 + 无结果时误报）。详见 `PLAN_P3_EVAL.md`。

**P3.4 已完成（2026-10-27）**：50 篇 / 383 段语料、真实后端链路，`recall@5 = 0.882`、
引用可追溯 100%（64/64），**P3 收口**。评估推翻 P3.0 的"空查询不会误报"，
并倒逼出两条检索规则（命中 ≥2 个 bigram、多词查询 token 级 AND）。
P3.5 向量检索判定不做。详见 `PLAN_P3_EVAL.md` §8。

## 2. 目标与边界

**要做**

- 把一篇资料（新闻、公告、研报摘录、自己的笔记）导入库，自动切成可检索的片段。
- 用关键词找到相关片段，看得到它出自哪篇、第几段、原文是什么。
- AI 回答时能引用到具体片段，而不是说"据报道"。
- 重复导入同一篇能被拦住；删资料时片段一起删。

**不做（P3 第一版）**

- 不做爬虫、不做定时抓取新闻。理由见 D1。
- 不做 HTML / PDF 导入（P3.1）：两者都要独立的正文提取，先看关键词检索在你的真实资料上够不够用，
  再决定为哪种格式引入依赖。上传这两类文件时接口会明确拒绝并说明替代做法。
- 不做多用户与权限。
- 不做"资料问答"的独立聊天页——复用 P2 的 AI 助手，只多一个工具。已登记到 `BACKLOG.md §2.2`（前置：检索质量达标；与「不做多轮记忆」有张力，真做要先定出处标注规则）。
- 不做实体识别、自动打标签、自动关联标的。标签和关联都是手动的。

## 3. 关键决策

**先定义两个词**（后面反复用到）：

- **入口**：一篇资料以什么形式交进系统。指数据入口，不是页面入口。可选的有粘贴、本地文件、PDF、URL 四种。
- **独立的资料问答页**：一个只对资料库提问的聊天页（"根据我存的资料回答…"），与现有 AI 助手是两套界面。

| # | 问题 | 决定 | 理由 |
|---|---|---|---|
| D1 | 资料从哪来 | **手工粘贴 + 本地文件（md/txt）**；HTML 与 PDF 都延后，URL 抓取不做 | 项目里没有验证过的新闻/公告源，爬虫是另一个工程。HTML 正文提取要引入解析库再自己写选择器启发式（导航、评论、广告），而"复制正文粘贴"已经覆盖了存网页内容的场景；PDF 是版面解析问题，另算一批（见 P3.2）。先让"人愿意存的资料"能进能查，再谈自动采集 |
| D2 | 要不要 pgvector | **P3.1–P3.4 不用**；P3.5 视评估结果决定 | 当前镜像是 `postgres:16-alpine`，**镜像里没有 vector 扩展的二进制**，`CREATE EXTENSION vector` 会直接报 `extension "vector" is not available`；要装得换成 `pgvector/pgvector:pg16` 或自建镜像。更关键的是：中文全文检索的短板在**分词**，不在相似度。换向量是"绕开分词"，代价是 embedding 成本、离线不可用、引用更难保证——先把关键词做扎实 |
| D3 | 中文怎么切词 | 应用层 **bigram**，检索用 `ILIKE` 组合，不上 `zhparser`/`pg_bigm`；**不做停用词过滤** | `zhparser`、`pg_jieba` 都要源码编译，Windows 本地装扩展是长期维护负担；`simple` 分词对中文等于不切词。bigram（"渠道库存" → 渠道/道库/库存）零依赖，配合现有 `ILIKE` 就能用。停用词经评估实测只提升 precision 0.008，不值得维护词表（见 `PLAN_P3_EVAL.md` §3） |
| D4 | 切片策略 | 按 Markdown 标题 + 段落切，目标 300–600 字，重叠 80 字，**保留 `char_start`/`char_end`** | 片段太短丢上下文，太长检索排名失真。偏移量是"引用可追溯"的基础：能定位回原文第几段 |
| D5 | 去重 | `content_hash = sha256(规范化正文)` 唯一索引，冲突返回 `409` + 已存在的文档 id | 同一篇粘两次是最常见的误操作。规范化 = 去首尾空白、压缩连续空行、统一换行符 |
| D6 | 权限 | 不做 | 单用户本地部署，没有"谁能看"的问题。但每篇必须记录 `source_type` / `source_ref` / `imported_at`——**来源与时间比权限重要** |
| D7 | 删除联动 | `library_chunk.document_id` 外键 `ON DELETE CASCADE` | 片段脱离文档就没有意义，不能留孤儿 |
| D8 | 引用怎么保证不编 | 模型只能引用**检索返回的片段 id**；引用文本由后端按片段原文拼装 | 与日记回顾同一条规矩：模型自述的出处一概不采信。这条是 P3 验收"引用可追溯"的唯一实现方式 |

### 3.1 后期再上向量，到底难在哪（可逆性分析）

判断"现在不上会不会锁死"，逐项看后期要动什么：

| 后期要做的事 | 实际成本 | 会不会变难 |
|---|---|---|
| 数据库支持向量 | 换镜像 + `CREATE EXTENSION vector`，一次性 | 不会。有 `pg_dump` 备份，切完验证即可 |
| 表结构加向量列 | `ALTER TABLE library_chunk ADD COLUMN embedding vector(1024)`，附加列，不动现有数据 | 不会 |
| 已有资料补向量 | 个人规模约 1000 篇 × 10 片段 = 1 万条：本地模型（如 bge-m3）跑几十分钟，或用 API 约几美分 | 不会。是一次性批处理，脚本可重跑 |
| 检索改成混合 | 关键词召回 + 向量召回合并去重，返回结构不变（仍是 `chunkId`） | 不会，只要返回结构里有稳定的 `chunkId` |

**真正会让后期变难的三件事，以及我们怎么避开**：

1. **不切片，直接拿整篇文档检索** → 后期要补切片、重算引用位置、重算全部向量，是重构。
   → 我们 P3.1 就切片，并保留 `char_start` / `char_end`。
2. **引用靠模型自述或靠检索时的 `snippet`** → 换检索方式后引用就对不上原文。
   → 我们把引用定义成"按 `chunkId` 回原文取完整片段"，与检索方式无关。
3. **把某一代 embedding 模型的维度写进表结构** → 换模型要重算全库 + 改列维度。
   → 记录 `embedding_model` + `embedding_dim` 到配置或表里，列宽跟着模型走，不写死在代码里。

结论：**现在这套设计（切片 + 偏移 + 稳定 `chunkId` + 引用回原文）恰好是把"后期加向量"成本压到最低的形状。** 反过来，为了"以后好换"而提前上向量，要先付 embedding 费用、多维护一个模型服务，而效果好坏没有评估集可判断——那才是真的冒险。

## 4. 数据模型（V9 草案）

```sql
-- 资料文档：一篇 = 一次导入
CREATE TABLE library_document (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title         TEXT        NOT NULL,
    source_type   TEXT        NOT NULL,              -- PASTE / FILE / URL（URL 预留）
    source_ref    TEXT,                              -- 文件名或 URL，粘贴时为空
    publisher     TEXT,                              -- 券商 / 媒体 / 自撰
    published_at  TIMESTAMPTZ,                       -- 资料本身的时间（可能未知）
    imported_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    content       TEXT        NOT NULL,              -- 规范化后的全文
    content_hash  TEXT        NOT NULL,              -- sha256(content)
    char_count    INT         NOT NULL,
    status        TEXT        NOT NULL DEFAULT 'ACTIVE',  -- ACTIVE / ARCHIVED
    note          TEXT
);
CREATE UNIQUE INDEX ux_library_document_hash ON library_document (content_hash);

-- 片段：检索与引用的最小单位
CREATE TABLE library_chunk (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    document_id  BIGINT NOT NULL REFERENCES library_document (id) ON DELETE CASCADE,
    seq          INT    NOT NULL,                    -- 文档内序号，从 1 开始
    heading      TEXT,                               -- 所属标题（Markdown 标题或首句）
    content      TEXT   NOT NULL,
    char_start   INT    NOT NULL,                    -- 在原文中的起始偏移
    char_end     INT    NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (document_id, seq)
);
CREATE INDEX ix_library_chunk_document ON library_chunk (document_id);

-- 资料与标的的关联（手动）
CREATE TABLE library_document_instrument (
    document_id   BIGINT NOT NULL REFERENCES library_document (id) ON DELETE CASCADE,
    instrument_id BIGINT NOT NULL REFERENCES instrument (id),
    PRIMARY KEY (document_id, instrument_id)
);
```

不做全文索引的理由：数据量是个人级（几百到几千篇），`ILIKE` 在 `content` 上全表扫足够；上 `tsvector` 要先解决中文分词，收益不如先把 bigram 检索做对。等 P3.4 评估后发现"慢"再补 `pg_trgm` 索引（它不需要换镜像，`postgres:16-alpine` 自带）。

## 5. 任务分解

### P3.0 召回验证（S，半天）✅ 已完成（2026-10-27，见 `PLAN_P3_EVAL.md`）

先回答一个问题：**bigram + ILIKE 能不能满足个人资料检索**。

- 实际做法：6 篇合成资料（37 段）、21 条查询（含 2 条应无结果），对比整词 `ILIKE`、bigram、`pg_trgm`、
  bigram+停用词、bigram+命中阈值五种策略，算 `recall@5` / `precision@5` / 空查询正确率。
- 结论：bigram `recall@5 = 0.974`、`precision@5 = 0.631`，过门槛；`pg_trgm` 淘汰（0.763 且误报 1 条）；
  停用词与命中阈值都不采用（前者收益 0.008，后者把长句查询打到空结果）。
- 脚本：`scripts/p3_eval/run_eval.py`（临时表 + `ROLLBACK`，不写业务库），P3.4 复用并把语料换成真实资料。

### P3.1 导入与切片（M）✅ 已完成（2026-10-27）

- `POST /library/documents`：`{"title","sourceType","sourceRef","publisher","publishedAt","content","instrumentIds":[]}`；
  服务端按 order 做 规范化 → sha256 → 去重(409) → 切片 → 落库，**同一事务**。
- `POST /library/documents/import`：上传 `.md` / `.markdown` / `.txt`（multipart），UTF-8 读取后走同一条路径。
  范围调整：**HTML 不做**（要引入解析库再写选择器启发式，而粘贴已覆盖网页场景），
  `.html` / `.pdf` 明确拒绝并说明替代做法。
- 切片器 `LibraryChunkSplitter`：段落边界优先、300–600 字、**整段重叠**（不是按字数截 80 字，
  那会让偏移指向半个句子）；超长段落退到句子，仍超长按 600 字硬切。纯逻辑，9 项单测覆盖
  （空文本、短文本、多级标题、超长无标点、单行、重叠、偏移一致性）。
- `GET /library/documents`（分页 + 关键词，**不返回正文**）、`GET /library/documents/{id}`（含片段）、
  `DELETE /library/documents/{id}?confirm=true`（未确认返回 400 并给出将删的片段数）。
- 表：`V9__library.sql` 建 `library_document` / `library_chunk`（`ON DELETE CASCADE`）/ `library_document_instrument`。
- 前端 `/library`：左列表右详情，粘贴弹窗、上传、删除；侧边栏新增「资料」组。
- 验收（实测 8082）：粘一篇成功、重复导入 409 且提示带 id、md 导入成功、pdf/html 被拒并说明原因、
  删除未确认 400、确认后片段级联清零。
- 测试：`LibraryChunkSplitterTest` 9 项、`LibraryServiceTest` 9 项。

### P3.2 检索（M）✅ 已完成（2026-10-27）

- `GET /library/search?keyword=&limit=&instrumentId=`：bigram 拆词 → `ILIKE` 组合 → 排序。
- 与计划的三处偏差，都是实测倒逼的：
  1. **排序没算"片段长度"**，改成 `score = 整词命中×3 + bigram 命中数`。片段长度与相关性无关，
     短片段本来命中率就低，再按长度加权会让"讲得最详细的那段"排后面。
  2. **检索列是「标题 + 正文」**，不只正文。否则"我记得有篇讲渠道库存的"这类查询，
     遇到标题有词、正文没词的资料就永远搜不到。
  3. **同篇最多 3 个片段，且"仅标题命中"的片段按篇收窄**。不限的话搜"调研纪要"会返回同一篇三段，
     其中两段正文里根本没这个词。
- 返回：`chunkId` / `documentId` / `documentTitle` / `seq` / `heading` / `snippet`（命中位置前后各 60 字）/
  `charStart` / `charEnd` / `sourceType` / `sourceRef` / `publisher` / `publishedAt` / `importedAt` /
  `score` / `matchedTerms` / `titleMatched`。
- 前端 `/library`：搜索框改为查片段，命中片段列表（关键词高亮）+ 点击定位到正文那一段（正文按片段渲染，
  重叠部分用游标裁掉），不新建页面。
- 验收（实测 8082 三篇短文 + 一篇 1855 字长文）：搜"渠道库存"命中 3 篇 6 段且长文只出 3 段；
  搜"600519"命中含代码的那段且 `matchedTerms` 只有 `600519`；搜"调研纪要"命中 2 篇（其中一篇标"仅标题命中"）；
  搜不存在的词返回空；空关键词 400；`limit=9999` 被截到 50。
- 测试：`LibrarySearchTermsTest` 13 项、`LibraryServiceSearchTest` 11 项。
- 已知：`ILIKE` 是全表扫描。个人资料规模（几千片段）在毫秒级；到十万片段再考虑 `pg_trgm` GIN 索引，
  现在加只是增加一个用不上的依赖。

### P3.3 Agent 工具接入（S）✅ 2026-10-27

- 新增工具 `library-search`：`GET /agent/tools/library/search?keyword=&limit=`，与 `diary-search` 同构。
- Python `java_tools.py` 白名单与 `AgentToolController` 两处同步改；`AgentToolControllerTest` 的映射断言要跟着更新。
- 助手侧：关键词规划里加入"资料"意图（问"之前那篇研报怎么说"时选这个工具）。
- 引用格式统一为 `《标题》· 第 N 段`，**由后端按 `chunkId` 拼装**；模型输出里若出现未命中的出处，整段替换为命中列表（复用 `accept_review` 的思路）。
- 验收：问"我存的资料里关于渠道库存怎么说"能取到片段；库里没资料时，回答必须说"没有相关资料"，不能拿模型知识冒充。

实现记录（与计划的偏差）：

- **引用校验比计划更严**：不只校验标题，还校验段号——"《纪要》· 第 9 段"而这篇只有 3 段，同样是编造的出处
  （`library_guard.py`，按"允许清单"裁剪而非"坏清单"：同篇的第 2 段是好的，只删第 9 段那一句）。
- **零命中时干脆不调模型**，比"让模型直说没有"更可靠：`degraded` 写明原因，结论固定为
  "资料库里没有找到与「X」相关的资料"。命中时系统提示第 5 条要求原样照抄 citation，减少误删。
- 关键词剥不出主题词时**不检索**（"看看我的资料"不触发工具）：拿整句去搜，命中全是噪声。
- 响应新增 `citations[]`（chunkId/documentId/seq/citation），前端渲染成胶囊标签，
  点击跳 `/library?doc={id}&chunk={seq}` 定位到那一段；资料页用完即把参数从地址栏抹掉。

### P3.4 评估与收口（S）✅ 2026-10-27

- 评估集：20 条查询 × 人工标注的相关片段（沿用 P3.0 的语料，扩到 50 篇）。
- 指标：`recall@5`、引用正确率（引用片段确实包含该结论）、无结果查询的误报率。
- 写进 `PLAN_P3_EVAL.md`，并在 `API.md` / `UI.md` / `README.md` 补文档。
- **决策点**：`recall@5 ≥ 0.8` 且引用正确率 100% → P3 收口；低于这条线，先优化 bigram 与排序，不上向量。

**结果（详见 `PLAN_P3_EVAL.md` §8）**：50 篇 / 383 段 → 切片成 125 个片段，
`recall@5 = 0.882`、引用可追溯 `64/64 = 100%`、citation 格式 `62/62`，**收口**。

评估过程中修正了两处实现（都是 P3.0 没暴露的）：

1. `minGramHits = 2`：长查询会拆出「周期」「变化」这类通用 bigram，只靠一个碎片命中就返回，
   导致三条应无结果的查询各返回 5 条噪声。试过按 30% 比例设门槛，recall 掉到 0.721，
   与 P3.0 否掉「半数阈值」同因——**门槛只能是绝对值**。
2. 多词查询做 token 级 AND：搜「黄金 ETF 持仓变化」时，纯 ETF 笔记靠 ET/TF 就能进结果。
   第一版误伤了「600519 三季报」，根因是语料那篇三季报没写代码（已修语料），修好后规则放回。

仍存在的问题：长句空查询会误报（「氢能电解槽订单」返回 2 段）、排序同分时靠发布时间、
precision 0.382 是下界。均已记入 §8.7 局限，排序改进登记 `BACKLOG.md`。

### P3.5 向量检索（M，可选）❌ 判定不做

前置：P3.4 判定关键词召回不足，且确认愿意换镜像。

**P3.4 已判定召回足够（0.882 ≥ 0.80），本批不做。** 后期若要做，成本见 §3.1：
切片、偏移、稳定 `chunkId` 都已就位，加向量是附加列 + 混合召回，不是重构。

- 镜像从 `postgres:16-alpine` 换到 `pgvector/pgvector:pg16`，验证现有数据卷可挂载、`CREATE EXTENSION vector` 成功、Flyway 迁移不受影响。
- 新增 `library_chunk.embedding vector(1024)`，导入时异步补 embedding（失败不阻塞导入，标记 `embedding_status`）。
- 检索走混合：关键词召回 + 向量召回 → 合并去重 → 仍用同一套片段返回结构。**引用规则不变**。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 中文 bigram 召回不稳（"渠道库存"被切成"渠道/道库/库存"，命中词数虚高） | 排序失真，用户觉得搜不准 | 停用词表 + 长词优先（整词命中权重 2、bigram 权重 1）；P3.0 先验证再动手 |
| 换镜像导致数据卷不兼容 | 本地库打不开，最坏丢数据 | P3.5 前置动作：`pg_dump -Fc` 备份 + 在临时容器验证挂载，通过再切 |
| HTML/PDF 解析出的正文带导航与页脚 | 切片里全是噪声，检索质量差 | P3.1 只收 md/txt；HTML 与 PDF 在接口层明确拒绝并说明"复制正文后粘贴"，不硬塞 |
| 引用片段被截断后语义变了 | "引用可追溯"名存实亡 | 引用永远按 `char_start/char_end` 回原文取完整片段，不用检索时的 `snippet` |
| 资料里有个人隐私或未公开信息 | 泄露风险（AI 调用会把片段发给模型） | 页面上明确写"检索到的片段会随问题发给模型"；`limitations` 里固定带这一条 |
| 资料量涨到几千篇后 `ILIKE` 变慢 | 检索列表卡 | 先加 `pg_trgm` 索引（自带，不换镜像）；仍不够再进 P3.5 |

## 8. 明确不做

- **爬虫与自动采集**：频率、反爬、解析漂移、版权，任何一条都够单独做一个项目。
- **多用户与权限**：没有登录体系，做权限是空转。
- **自动实体识别与自动打标签**：误标比不标更糟，标签全部手动。
- **独立的"资料问答"聊天页**：复用 AI 助手，只加工具。多一个页面就多一套状态与降级逻辑。
- **图片、表格、图表的解析**：PDF 里的图表是图片，P3 不碰。
