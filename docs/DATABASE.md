# StockCat 数据库设计

- 文档版本：V1.0-Draft
- 数据库：PostgreSQL
- 说明：本文件是逻辑模型草案；字段可在编码前评审，但所有 API 与实现必须同步更新。

## 1. 设计原则

- 使用 PostgreSQL 原生 `BIGINT`/`UUID` 主键方案二选一。本草案统一使用 `BIGINT GENERATED BY DEFAULT AS IDENTITY`，便于个人项目调试。
- 金额、价格、百分比使用 `NUMERIC`，不使用浮点数保存财务值。
- 时间戳统一保存为 `TIMESTAMPTZ`，应用以 UTC 存储，界面按用户时区显示；供应商原始时间与本系统采集时间分开。
- 标的代码与市场共同构成唯一业务标识。
- 对业务事件使用快照字段保留当时的规则上下文，避免规则删除/修改后历史事件无法解释。
- 由 Java 负责权威业务表写入和数据库迁移。

## 3. P0 表结构

### 3.1 `instrument`

- `id BIGINT PK`
- `market VARCHAR(16) NOT NULL`：如 `CN_A`
- `symbol VARCHAR(32) NOT NULL`：供应商/市场约定代码
- `name VARCHAR(128) NOT NULL`
- `instrument_type VARCHAR(16) NOT NULL`：`STOCK`、`ETF`、`LOF`
- `currency CHAR(3) NOT NULL DEFAULT 'CNY'`
- `source_code VARCHAR(32)`：默认行情来源标识
- `enabled BOOLEAN NOT NULL DEFAULT TRUE`
- `created_at TIMESTAMPTZ NOT NULL`
- `updated_at TIMESTAMPTZ NOT NULL`
- 唯一约束：`UNIQUE(market, symbol)`

### 3.2 `watchlist_item`

- `id BIGINT PK`
- `instrument_id BIGINT NOT NULL FK -> instrument.id`
- `created_at TIMESTAMPTZ NOT NULL`
- 唯一约束：`UNIQUE(instrument_id)`（P0 单用户）
- 删除自选不自动删除标的主数据和历史行情。

### 3.3 `quote_snapshot`

- `id BIGINT PK`
- `instrument_id BIGINT NOT NULL FK -> instrument.id`
- `source_code VARCHAR(32) NOT NULL`
- `last_price NUMERIC(20, 6)`
- `previous_close NUMERIC(20, 6)`
- `change_percent NUMERIC(12, 6)`：单位为百分数值，例如 `2.5` 表示 `2.5%`
- `volume NUMERIC(24, 4)`
- `turnover NUMERIC(24, 4)`
- `market_time TIMESTAMPTZ`：数据源行情时间
- `collected_at TIMESTAMPTZ NOT NULL`
- `data_status VARCHAR(16) NOT NULL`：`VALID`、`STALE`、`PARTIAL`、`INVALID`
- `raw_payload JSONB`：可选，限制体积并避免保存无必要的敏感信息
- 索引：`(instrument_id, collected_at DESC)`；`(collected_at DESC)`
- P0 可只保留合理时间窗口的快照；保留策略由配置决定。

### 3.4 `trading_calendar`

- `id BIGINT PK`
- `market VARCHAR(16) NOT NULL`
- `trade_date DATE NOT NULL`
- `is_trading_day BOOLEAN NOT NULL`
- `session_json JSONB`：当日交易时段，可为空并使用市场默认规则
- `source_code VARCHAR(32)`
- `updated_at TIMESTAMPTZ NOT NULL`
- 唯一约束：`UNIQUE(market, trade_date)`
- P0 先覆盖 A 股；节假日数据需要来源校验和年度更新机制。

### 3.5 `alert_rule`

- `id BIGINT PK`
- `name VARCHAR(128) NOT NULL`
- `instrument_id BIGINT NOT NULL FK -> instrument.id`
- `rule_type VARCHAR(32) NOT NULL`：**可插拔的规则类型标识**，不同标的可搭配不同类型。
  已实现：`PRICE_ABOVE`、`PRICE_BELOW`、`CHANGE_PERCENT_ABOVE`、`CHANGE_PERCENT_BELOW`（盘中评估）；
  `MACD_GOLDEN_CROSS`、`MACD_DEATH_CROSS`、`KDJ_GOLDEN_CROSS`、`KDJ_DEATH_CROSS`、`RSI_CROSS_ABOVE`、`RSI_CROSS_BELOW`（收盘后评估）。
  待实现：`PREMIUM_ABOVE`、`PREMIUM_BELOW`（等 IOPV 数据接入）。
- `params JSONB NOT NULL`：规则参数，结构由 `rule_type` 决定，Java 侧按类型校验：
  - 价格类：`{"threshold": 10.5}`
  - 涨跌幅类：`{"threshold": -20}`（百分数值，跌 20% 为 -20）
  - 溢价率类（P1）：`{"threshold": 2.0}`
  - 指标类（P1）：`{"indicator":"MACD","fast":12,"slow":26,"signal":9,"direction":"golden"}`
- `cooldown_seconds INTEGER NOT NULL DEFAULT 1800`（V3 起以秒为单位，支持秒/分钟/小时粒度；原 cooldown_minutes 已迁移换算）
- `enabled BOOLEAN NOT NULL DEFAULT TRUE`
- `last_triggered_at TIMESTAMPTZ`
- `created_at TIMESTAMPTZ NOT NULL`
- `updated_at TIMESTAMPTZ NOT NULL`
- 校验：`cooldown_seconds >= 0`；`params` 必须通过该 `rule_type` 的参数 schema 校验；创建时校验该类型所需数据已接入（如溢价率规则要求 IOPV 数据可用），否则拒绝，避免建了永不触发的"死规则"。
- 索引：`(enabled, instrument_id)`
- 扩展方式：新增规则类型 = 新增一个 `rule_type` 值 + 一个 evaluator 实现 + 一个参数 schema，**不修改表结构**。
- 去重键格式随输入类型不同：行情类 `rule-{id}-{触发分钟}`（同一分钟内不重复），指标类 `rule-{id}-{交易日}`（一天一次）。
- 多规则语义：**同一标的可挂任意多条规则**（`instrument_id` 无唯一约束），每条规则独立评估、独立冷却、独立产生事件与通知；同一时刻多条规则同时满足时生成多条并列的 `alert_event`，不合并。

### 3.6 `alert_event`

- `id BIGINT PK`
- `rule_id BIGINT`：允许规则删除后置空
- `instrument_id BIGINT NOT NULL FK -> instrument.id`
- `rule_name_snapshot VARCHAR(128) NOT NULL`
- `rule_type_snapshot VARCHAR(32) NOT NULL`
- `condition_params_snapshot JSONB NOT NULL`：触发时规则参数完整快照，规则删除/修改后历史事件仍可解释
- `observed_price NUMERIC(20, 6)`：触发时价格（价格类规则）
- `observed_change_percent NUMERIC(12, 6)`：触发时涨跌幅
- `observed_detail JSONB`：其他类型规则的观测值（如溢价率 2.3、MACD 柱值），结构由 rule_type 决定
- `quote_market_time TIMESTAMPTZ`
- `triggered_at TIMESTAMPTZ NOT NULL`
- `deduplication_key VARCHAR(160) NOT NULL`
- `created_at TIMESTAMPTZ NOT NULL`
- 唯一约束：`UNIQUE(deduplication_key)`，具体 key 生成规则由 Java 服务定义。
- 索引：`(triggered_at DESC)`、`(instrument_id, triggered_at DESC)`

### 3.7 `notification_record`

- `id BIGINT PK`
- `alert_event_id BIGINT FK -> alert_event.id`（P0.6 起可空：测试发送的通知不关联事件，见 V2 迁移）
- `channel VARCHAR(24) NOT NULL`：`EMAIL`、`SERVERCHAN` 或 `PUSHPLUS`（最终只实现已验证渠道）
- `status VARCHAR(16) NOT NULL`：`PENDING`、`SENT`、`FAILED`
- `provider_message_id VARCHAR(128)`
- `attempt_count INTEGER NOT NULL DEFAULT 0`
- `last_error_code VARCHAR(64)`
- `last_error_message VARCHAR(512)`：不得包含密钥
- `created_at TIMESTAMPTZ NOT NULL`
- `sent_at TIMESTAMPTZ`
- 索引：`(alert_event_id)`、`(status, created_at)`

### 3.8 `monitor_target`（监控标的）
- `id BIGINT PK`
- `instrument_id BIGINT NOT NULL FK -> instrument.id`
- `enabled BOOLEAN NOT NULL DEFAULT TRUE`
- `created_at TIMESTAMPTZ NOT NULL`
- 唯一约束：`UNIQUE(instrument_id)`
- 说明：监控标的集合决定采集与告警评估范围，与自选列表相互独立；首页指数行情使用内置配置（如上证指数），不占用本表。

### 3.9 `trade_record`（交易流水）
- `id BIGINT PK`
- `instrument_id BIGINT NOT NULL FK -> instrument.id`
- `direction VARCHAR(8) NOT NULL`：`BUY` / `SELL`
- `price NUMERIC(20,6) NOT NULL`：成交价
- `quantity NUMERIC(24,4) NOT NULL`：成交数量（股），必须 > 0
- `fee NUMERIC(20,6) NOT NULL DEFAULT 0`：佣金/税费合计
- `trade_time TIMESTAMPTZ NOT NULL`：成交时间
- `note VARCHAR(512)`：备注（操作理由等）
- `created_at` / `updated_at TIMESTAMPTZ NOT NULL`
- 校验：`price > 0`；`SELL` 时本方向数量不得超过该时点前计算出的持有数量（由 Java 校验）。
- 索引：`(instrument_id, trade_time)`、`(trade_time DESC)`

### 3.10 持仓计算规则（不建表，由 Java 聚合 `trade_record` 得出）

按 `trade_time` 升序对每只标的重放流水：

- **买入**：`持仓数量 += quantity`；`摊薄成本 = (原持仓数量×原摊薄成本 + quantity×price + fee) / 新持仓数量`（费用计入成本）。
- **卖出**：校验 `quantity <= 当前持仓数量`，否则拒绝；`已实现盈亏 += (price − 摊薄成本)×quantity − fee`；`持仓数量 -= quantity`。
- **市值** = 当前数量 × 最新有效快照价（快照缺失/过期时市值与浮动盈亏显示为"—"，不按 0 计算）；**浮动盈亏** = 市值 − 数量×摊薄成本。
- 全部清仓后成本清零，再次买入重新起算。
- 计算逻辑必须有单元测试覆盖：多笔买入、部分卖出、清仓后再买入、超卖拒绝、费用计入成本。

### 3.11 `market_recap`（市场复盘）
每个交易日一篇，关注"市场主要情况 + 不同板块表现"。
- `id BIGINT PK`
- `recap_date DATE NOT NULL`：复盘对应的交易日，`UNIQUE(recap_date)`（一天一篇）
- `title VARCHAR(128) NOT NULL`
- `market_summary TEXT`：市场主要情况（可空，正文的一部分）
- `sector_notes TEXT`：板块表现记录（可空）
- `content TEXT NOT NULL`：完整正文（Markdown）
- `related_alert_event_ids JSONB`：关联告警事件 id 数组，可为空
- `status VARCHAR(16) NOT NULL DEFAULT 'MANUAL'`：`MANUAL`（手工）/ `AI_DRAFT`（AI 草稿，P2）
- `created_at` / `updated_at TIMESTAMPTZ NOT NULL`
- 索引：`(recap_date DESC)`
- 说明：`market_summary`/`sector_notes` 是结构化提示字段，供编辑页分区填写与 AI（P2）取数，正文仍是完整 `content`。

### 3.12 `diary_node`（我的日记：树状长期笔记本）
仿飞书文档的树状目录：文件夹与文档统一为一棵树，长期沉淀、不按日期组织。
- `id BIGINT PK`
- `parent_id BIGINT`：父节点 id，NULL 为根级；`FK -> diary_node.id`
- `node_type VARCHAR(8) NOT NULL`：`FOLDER` / `DOC`
- `title VARCHAR(128) NOT NULL`
- `content TEXT`：正文，仅 `DOC` 有；`FOLDER` 恒为 NULL
- `related_instrument_ids JSONB`：关联标的 id 数组，可为空
- `sort_order INTEGER NOT NULL DEFAULT 0`：同级排序
- `created_at` / `updated_at TIMESTAMPTZ NOT NULL`
- 约束与校验：
  - 树深度限制 ≤ 5 层（Java 校验，防失控嵌套）。
  - 不能把节点移动到自己或自己的子孙下（成环检测，Java 校验）。
  - `FOLDER` 的 `content` 必须为 NULL。
- 索引：`(parent_id, sort_order)`
- 删除：删除 FOLDER 默认级联删除整棵子树，API 需 `?confirm=true` 且前端强确认；DOC 单独删除即可。
- 检索：P0 对 DOC 的 `title`/`content` 做 `ILIKE` 关键词检索；全文检索 P3 再评估。
- 与市场复盘的关系：两者分开存储；`related_instrument_ids` 可表达同一标的的关联，但不做外键级联。

## 4. P1/P2 扩展表概要

### `kline_daily`（P1.2 已实现，迁移 V4）

P1 只做日线（决策 D3），表名直接叫 `kline_daily`，不引入 `interval_code` 多周期维度。

- `id`, `instrument_id` FK, `trade_date DATE`, `adjust`（`qfq`/`hfq`/`raw`），`open`/`high`/`low`/`close` `NUMERIC(20,6)`,
  `volume`（手）/ `amount`（元）, `change_percent`, `turnover_rate`, `source_code`, `fetched_at`
- 唯一约束：`UNIQUE(instrument_id, trade_date, adjust)`；同步用 **UPSERT**。
  理由（决策 D4）：**前复权的历史值会随除权整体移动**，只做增量 INSERT 会让除权前的历史价格永久错误。
- 约束：`open/high/low/close > 0` 与 `high >= low`。前复权长窗口会把早期价格算成负数（实测茅台 2001-08-27 为 -312.68），
  Java 侧先拦截，DB 再兜一层。
- 索引：`(instrument_id, adjust, trade_date DESC)`
- 不落库的：指标值（决策 D2，查询时计算）、上游未收盘的当日 K 线（写入前由 Java 拒绝）。

原 `kline` 表设计（含 `interval_code`、`bar_time`，唯一键含 `source_code`）保留作 P3 多周期扩展参考；
届时若支持分钟线，新建 `kline_minute` 而非改造 `kline_daily`。

### `indicator_result`

- `id`, `instrument_id`, `interval_code`, `indicator_code`, `parameters_json JSONB`, `value_json JSONB`, `bar_time`, `calculated_at`, `engine_version`
- 唯一约束应包含标的、周期、指标、参数和 bar 时间；实现时需确定参数规范化方式。
- 指标由 Java 统一计算（P1 实际做法是**不落库**、按查询现算，见 `PLAN_P1.md` D2；本表仅作为将来需要缓存时的设计参考）。

### `fund_reference`（P1.4 已实现，迁移 V5）

一行 = 一个基金在一个交易日的观测。**溢价率不落库**（它依赖当下价格，存下来就会过期），查询时现算。

- `id`, `instrument_id` FK, `trade_date DATE`（行情日期；净值补写行的 trade_date = nav_date）
- `price`（采集当时价格，用于事后核对"当时溢价"）、`iopv`、`iopv_time`（仅 ETF，盘中每 15 秒刷新）
- `nav`、`nav_date`（单位净值与净值所属日期，来自天天基金 lsjz；**必须有日期才展示/参与溢价计算**）
- `market_source_code` / `nav_source_code`：两个来源分开记——IOPV 来自腾讯，净值来自天天基金，
  用一列表达必然要说谎
- 约束：`UNIQUE(instrument_id, trade_date)`（盘中反复刷新与晚间补净值落在同一行，两条 UPSERT 都用
  `COALESCE(EXCLUDED.x, ...)`，先写的字段不会被后来的空值覆盖）；`nav/iopv/price` 非正值拒绝（DB 兜底）；
  `nav/iopv/price` 至少有一个非空
- 索引：`(instrument_id, trade_date DESC)`
- 写入时序：盘中随行情采集写 `price/iopv` → 晚间 21:30（+启动补跑）按最近 N 期 UPSERT `nav/nav_date`
- 数据形态示例：ETF 白天 = price+iopv（nav 为空）；晚上 = price+iopv+nav（溢价用 IOPV）；
  历史未同步行情的净值行 = 仅 nav

原 `fund_valuation` 概要表（含 `premium_rate`、`data_status` 列）作废：溢价率现算不落库，
数据状态由 `iopv_time` / `nav_date` 直接表达，不再需要单独的状态列。

### `position_snapshot`（P1.5 已实现，迁移 V6）

一行 = 一个标的在一个交易日的收盘持仓。**不是事实来源**：事实是 `trade_record` + `kline_daily`，
快照只是"按流水重放到那天"的结果，因此允许整段删除重建（重建 = 先删区间再插，不做增量修补）。

- `id`, `trade_date DATE`, `instrument_id` FK, `quantity NUMERIC(24,4)`, `avg_cost NUMERIC(20,6)`
- `cost_value`：持仓成本 = `quantity × avg_cost`（avg_cost 已含买入费用）。落库是为了聚合时不再乘一遍，
  也避免各调用点舍入不一致。
- `close_price`、`market_value`、`unrealized_pnl`：三者同时有值或同时为 `null`。取不到收盘价时留 `null`，
  **不按 0 汇总**（否则曲线会在某天突然塌下去）。
- `realized_pnl_cum`：**截至当日累计**已实现盈亏（摊薄成本法、已扣卖出费用），不是当日发生额。
  区间已实现 = 期末 − 期初。
- `price_adjust`：实际取价口径。**固定 `raw`（不复权）**——`avg_cost` 是真实成交价，
  前复权价随除权整体下移，两者直接相减会算出"每年亏一笔分红"的假曲线。
- `source_code`、`created_at`
- 约束：`UNIQUE(trade_date, instrument_id)`；`quantity >= 0`；`close_price IS NULL OR close_price > 0`
- 索引：`(trade_date DESC)`

日期轴 = 「该标的实际有收盘价的交易日 ∪ 有成交的日期」：停牌日沿用最近一个收盘价（floor），
节假日不会凭空多出点。清仓当天写一行 `quantity=0`（市值 0 是确定的），此后不再写行。

组合层（总市值/总成本/累计盈亏）**不建表**，按 `trade_date` 聚合本表即得。收益口径见 `docs/API.md` §6。

### `ai_recap`

- `id`, `recap_date`, `generated_at`, `model_name`, `input_range_json JSONB`, `content TEXT`, `source_summary_json JSONB`, `status`, `error_message`
- AI 输出需保留生成时间和所用数据范围。

## 5. 迁移与初始化

- 已定：使用 **Flyway** 做数据库迁移（Spring Boot 生态标配，纯 SQL 脚本，与 MyBatis 配合自然）。每个 schema 变更新增迁移文件，不在已应用迁移上直接改写。
- 开发环境提供 `.env.example` 和数据库初始化说明。
- 种子数据仅用于开发测试，必须标记为模拟数据；生产/真实模式不得把种子行情当成实时行情。
- 交易日历应有可追踪的数据来源和更新日期。

## 6. 删除与保留策略

- 删除自选只删除 `watchlist_item`。
- 删除规则不级联删除历史 `alert_event` 和 `notification_record`；事件中的快照字段保留历史语义。
- 标的若已有历史数据，优先停用而非物理删除。
- 行情快照保留期限：默认保留 **90 天**（可配置），到期数据由定期清理任务删除；`raw_payload` 仅保留 7 天或直接不启用。不在未确认需求前无限保留原始 payload。

## 7. 本地备份与初始化

- 备份：使用 `pg_dump`（自定义格式 `-Fc`）导出，本地开发建议每日一次或重要操作前手动执行；恢复用 `pg_restore`。备份文件不提交 Git。
- 初始化：新环境按顺序执行 ① `docker compose` 启动 PostgreSQL（或本机实例）→ ② 创建数据库与用户 → ③ 启动 Java 服务，Flyway 自动执行迁移建表。
- 种子/模拟数据：仅开发测试用，必须有明显标记（如标的名称前缀"模拟-"），不得被当成真实行情展示；真实模式启动时不应加载种子数据。
- 交易日历数据来源与更新日期记录在 `trading_calendar.source_code` / `updated_at`，便于追溯。
